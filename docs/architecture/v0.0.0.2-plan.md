## Confirmed gaps and proposed safeguards
- Dependency pins record initial installs rather than qualified tips; separate upstream source, installation, tested and archival refs.
- Validator checks count/authority but not exact allowed task IDs, cron grammar, timezone, schema version, target repository, unknown keys, missing fields or receipt consistency. Strict versioned schemas and semantic validation.
- TASKS.md, schedule.json and dashboard duplicate task facts. One canonical registry; generated Markdown and HTML with drift checks.
- No implementation of lease fencing, duplicate suppression, missed runs, retry/recovery or host delivery; define contracts and offline fixtures, do not claim enforcement.
- Graph archive bytes are in expiring artifact; preserve verified bytes or explicit durable storage and provenance. Validate graph coverage and exact full-line anchors.
- VIB verification hardcodes issue #1 only; append-only ledger progression must not invalidate earlier checkpoints. Freeze proof separate from continuing ledger.
- Workflows are branch-specific and standard hosted only; design explicit CI triggers for future checkpoint branches without adding default-branch cron. Public data must be sanitized. No secret IDs, logs, credentials, or private prompts.
- Product name may change; use stable internal IDs and repo identity rather than display name. Keep platform adapters optional; no mandatory Supabase, Notion or paid tooling.
- Existing tests cover only 5 scenarios per OS; add migration, contract, security, graph and offline behavior regressions.

## Proposed target structure (approval required)
```
README.md
WORKFLOW.md                # retained public entrypoint

  schedule.json            # single canonical registry
  dependencies.lock.json   # exact upstream/install/tested pins

  v1/                      # frozen wire contracts
  v2/                      # additive contract evolution if needed

  roles/                   # five role templates, composed with common rules

  policy/                  # pure authority/dedup/lease rules, no host writes
  evidence/                # receipts/provenance verification
  adapters/                # explicit capability boundaries; no automatic activation
  cli.py
dashboard/
  index.html               # generated or consumes sanitized read model
docs/
  architecture/
  decisions/
  migrations/
examples/
tests/
  unit/
  contract/
  regression/
  integration/
  fixtures/
tools/                     # thin compatibility wrappers, not duplicate logic

```
Avoid empty folders and speculative dependencies. Keep root compatibility wrappers/readme links until migration tested; do not duplicate authoritative files. Optional adapters are interfaces only unless separately approved.

## Approval gates
- [ ] Complete exact file/blob inventory across frozen branches; immutable SHA manifest and explicit known limitations.
- [ ] Approve folder responsibility, one-way dependencies, stable entrypoints, schema versions and compatibility map.
- [ ] Approve preservation/rollback strategy; no destructive migration, no duplicate sources, exact history preserved.
- [ ] Define negative test matrix: missing/unknown schema, wrong types, duplicate JSON keys, wrong IDs/authority/cron/timezone, path traversal/symlink/case collisions, stale SHA/pins, malformed receipts, missing proof, overlapping runs, stale lease/fencing, duplicate delivery, retries, missed runs, DST/UTC, private data leakage, unavailable adapters, graph drift, rollback.
- [ ] Public Ubuntu/Windows tests, exact-SHA logs and artifacts; Graphify/Veraphify map only after actual migration; no simulation represented as genuine host evidence.
- [ ] Head approves design before runtime migration; independent review and owner acceptance remain separate. No merge, closure, publishing or schedule changes implied.

Scope: architecture review and migration plan first. Implementation is pending layout approval.

## Migration procedure
1. Validate baseline blob inventory and preserve frozen references.
2. Approve path/ownership contract and stable IDs; document rollback.
3. Add schemas and regression fixtures before moving runtime code.
4. Move one responsibility at a time with compatibility wrappers and exact-source evidence. No duplicated authority.
5. Validate fresh checkouts on Ubuntu and Windows, migration/reverse migration, missing adapters, public-data sanitation and graph citations. Independent review before acceptance.

For optional Supabase, do not store raw private task payloads in the public repository. Default runtime is file/receipt based; any database adapter requires a separate owner decision, versioned migrations, least privilege, row-level security and access isolation tests. Dashboard renders only sanitized receipts and explicitly labels stale or unavailable data.
